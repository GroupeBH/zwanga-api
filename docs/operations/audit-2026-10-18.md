# Audit performance, fiabilité, robustesse et sécurité — 18 octobre 2026

## Conclusion

La compilation et la suite de tests exécutée passent, mais cela ne suffit pas à garantir la sécurité, la tenue en charge ou la haute disponibilité. Le point applicatif à corriger en premier est une course entre renouvellement de session et révocation : elle a été reproduite localement. Le KYC AWS automatique contrôle la cohérence des informations, mais ne dispose pas d'une vérification d'authenticité de la pièce. Le profil Terraform par défaut reste économique, sans redondance des trois composants principaux.

Cet audit ne constate pas une intrusion ni une panne actuelle en production. Il identifie des défauts du code, des risques de conception et des configurations à vérifier avant de conclure sur AWS.

- Dépôt backend local, base Git `d3fe7ab`, avec les changements non commités présents au début de l'audit, notamment la diffusion des demandes aux conducteurs et la migration `1780000074000`.
- Revue ciblée : authentification/OTP, KYC, autorisations financières, notifications, dispatch, traitements périodiques, accès PostgreSQL/Redis, journalisation, Docker et Terraform.
- Guides de revue sécurité TypeScript/Express et PostgreSQL utilisés pour vérifier les frontières d'autorisation, la durée des transactions et le moindre privilège. Le guide de rédaction a servi à structurer ce rapport dans la documentation existante.
- Aucun code applicatif, migration, fichier d'environnement, workflow CI/CD ou ressource AWS modifié. Seul ce rapport est ajouté.
- Pas de lecture des ressources AWS en direct pendant cet audit, pas de test de charge, pas d'appel réel OTP/KYC/paiement, pas d'audit de l'application mobile. Les seuils et valeurs Terraform ci-dessous sont ceux du dépôt, pas une attestation des valeurs déployées.

## Risques élevés

### AUD-01 — Une rotation de session peut annuler une révocation concurrente

**Domaine :** sécurité et fiabilité. **Confiance :** forte, reproduction locale.

**Preuves :** [auth.service.ts](../../src/auth/auth.service.ts), lignes 810–835 (`refreshToken`), 845–861 (`logout`), 488–520 (`resetPin`) et 1599–1627 (`generateTokens`).

Le refresh lit l'empreinte enregistrée, la vérifie, puis signe et enregistre de nouveaux jetons par un `UPDATE` inconditionnel. La lecture et l'écriture ne sont pas atomiques. Une déconnexion entre ces étapes met bien les jetons à `NULL`, mais le refresh peut ensuite les remplacer. Le verrou utilisé par la réinitialisation du PIN ne protège pas contre cette lecture antérieure faite hors transaction.

**Impact :** un refresh valide déjà en cours peut restaurer une session après déconnexion ou réinitialisation du PIN. Deux refresh concurrents peuvent également réussir et rendre immédiatement invalide l'une des réponses. Cela nécessite un jeton valide ou une requête déjà engagée ; ce n'est pas une création de session sans authentification.

**Reproduction observée :** lancement du refresh, pause au moment de signer, exécution de `logout`, reprise du refresh. Résultat : `revokedAtLogout=true`, puis `sessionRestoredAfterLogout=true`.

**Correction :** sérialiser la vérification et la rotation avec les révocations, ou utiliser une mise à jour conditionnelle sur l'empreinte attendue et vérifier `affected === 1`. Préserver les contrats HTTP existants. Ajouter des tests concurrentiels refresh/refresh, refresh/logout et refresh/reset PIN sur PostgreSQL isolé.

### AUD-02 — L'approbation KYC AWS ne vérifie pas l'authenticité du document

**Domaine :** sécurité métier/fraude. **Confiance :** forte sur les contrôles présents ; exposition conditionnée à l'activation du flux AWS.

**Preuves :** [aws-kyc.policy.ts](../../src/users/aws-kyc/aws-kyc.policy.ts), lignes 35–50 et fonction `inspectDocument` ; [aws-kyc.transport.ts](../../src/users/aws-kyc/aws-kyc.transport.ts), lignes 92 et 130 ; [aws-kyc.repository.ts](../../src/users/aws-kyc/aws-kyc.repository.ts), lignes 236–238.

La décision automatique combine pays/type reconnus par texte, noms, validité, confiance OCR, présence réelle et comparaison faciale. Le code indique lui-même que ces contrôles ne constituent pas une authentification de la pièce. Aucun signal d'authenticité documentaire n'est exigé par la décision automatique. Une forte confiance OCR signifie que le texte a été bien lu, pas que la pièce est officielle.

**Impact :** un document fabriqué ou modifié, portant un nom cohérent et le visage de son présentateur, pourrait satisfaire ces contrôles. L'essai synthétique confirme uniquement l'absence de ce critère dans la décision ; aucune image frauduleuse n'a été soumise à AWS.

**Correction :** définir les éléments permettant réellement l'approbation automatique pour les pièces RDC, compléter les contrôles documentaires et orienter vers une revue les cas sans preuve suffisante. Les gabarits, numéros et contrôles MRZ peuvent aider, sans constituer seuls une preuve d'authenticité. Conserver l'automatisation là où le risque est maîtrisé et validé sur des jeux de documents représentatifs.

AWS décrit Face Liveness comme une vérification probabiliste de présence, à associer à d'autres facteurs : [documentation Rekognition](https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness.html). Textract fournit des fonctions d'extraction et d'analyse : [documentation Textract](https://docs.aws.amazon.com/textract/latest/dg/how-it-works-analyzing.html).

### AUD-03 — L'API reçoit le compte administrateur PostgreSQL dans le Terraform

**Domaine :** sécurité, limitation de l'impact d'une compromission. **Confiance :** forte sur le câblage local ; droits déployés non inspectés.

**Preuves :** [database.tf](../../infra-aws/database.tf), ligne 23 ; [variables.tf](../../infra-aws/variables.tf), lignes 100–103 ; [ssm.tf](../../infra-aws/ssm.tf), lignes 16 et 98–104 ; [typeorm-options.ts](../../src/database/typeorm-options.ts), lignes 157 et 183.

Le même utilisateur sert à créer l'instance RDS et à construire `DATABASE_URL`, injectée dans l'application. Le support d'une `MIGRATION_DATABASE_URL` distincte existe côté CLI, mais ne sépare pas automatiquement les rôles dans l'infrastructure.

**Impact :** une compromission de l'API ou de ses identifiants aurait des conséquences plus larges que les seules opérations métier, notamment sur le schéma et les autres données accessibles au rôle.

**Correction :** préparer un rôle applicatif à privilèges minimaux et un rôle de migration séparé. Tester les droits nécessaires aux tables, séquences et fonctions avant de basculer ; ne pas retirer les droits actuels à l'aveugle en production. Cette séparation suit la [recommandation AWS sur le compte principal RDS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/UsingWithRDS.MasterAccounts.html).

### AUD-04 — Le profil Terraform par défaut n'est pas hautement disponible

**Domaine :** disponibilité et résilience. **Confiance :** forte sur les valeurs par défaut, pas sur l'état AWS réel.

**Preuves :** [variables.tf](../../infra-aws/variables.tf), lignes 124–127, 182–185 et 239–254 ; [redis.tf](../../infra-aws/redis.tf), lignes 20–24.

Valeurs par défaut : une tâche ECS, autoscaling désactivé, RDS sans Multi-AZ, un seul nœud Redis. Le failover Redis n'est activé que si le nombre de nœuds dépasse un. L'API dépend de PostgreSQL pour l'identité et de Redis pour des contrôles critiques, dont la limitation des requêtes.

**Impact :** la perte d'un composant peut interrompre le service jusqu'à sa récupération. Le redémarrage du conteneur et les healthchecks ne remplacent pas une réplique de base ou de cache.

**Correction :** vérifier les valeurs actuellement appliquées, puis planifier séparément la redondance ECS, RDS et Redis selon le budget. Dimensionner les pools cumulés avant d'ajouter des tâches. Aucun `terraform apply` ni changement CI/CD n'a été effectué dans cet audit.

## Risques modérés et points à traiter avant montée en charge

### AUD-05 — Contrôle KYC différent entre conduite et retraits

**Domaine :** cohérence des autorisations financières. **Confiance :** forte sur l'écart de requête ; présence de dossiers concernés en production non vérifiée.

**Preuves :** [driver-activation.ts](../../src/users/driver-activation.ts), lignes 10–17 ; [driver-settlements.service.ts](../../src/driver-settlements/driver-settlements.service.ts), lignes 1059–1065 ; [referrals.service.ts](../../src/referrals/referrals.service.ts), lignes 839–845.

La conduite demande que le dernier dossier soit approuvé. Les retraits de gains et de parrainage recherchent l'existence de n'importe quel dossier approuvé, sans choisir le dernier. Sur un compte ayant plusieurs dossiers, un ancien dossier approuvé peut donc satisfaire le contrôle alors qu'un plus récent est rejeté ou en attente.

**Impact :** états et autorisations contradictoires entre écrans et opérations. Les protections contre les doubles dépenses ne corrigent pas cet écart d'éligibilité.

**Correction :** définir une source de vérité commune pour le KYC courant, avec une politique explicite de revérification et de retrait des gains déjà acquis. Tester les historiques multi-fournisseurs et les événements tardifs ; ne pas bloquer silencieusement des gains légitimes sans règle de recours.

### AUD-06 — Dépendances de production affectées par des avis de sécurité

**Domaine :** sécurité et maintenance. **Confiance :** forte sur le résultat npm, exploitabilité à qualifier par chemin d'exécution.

**Preuves :** consultation npm du 18 octobre 2026, [package.json](../../package.json), notamment lignes 49, 73 et 85, et [package-lock.json](../../package-lock.json).

`npm audit --omit=dev` remonte 29 paquets affectés, dont 13 de sévérité élevée. Les chaînes concernées incluent Firebase/gRPC, PM2 et ses dépendances, ainsi que des instrumentations OpenTelemetry et des parseurs. Plusieurs paquets sont signalés par propagation d'un même avis.

**Impact :** dette de dépendances à traiter, mais pas preuve de 29 vulnérabilités accessibles à distance dans Zwanga. Le conteneur démarre directement `node dist/main.js`, pas PM2 ; les notifications utilisent `firebase-admin/messaging`, ce qui ne démontre pas l'utilisation des chemins Firestore/gRPC signalés. L'instrumentation activée doit également être vérifiée.

**Correction :** actualiser les correctifs compatibles, vérifier les dépendances inutilisées et tester les chemins réellement employés. Ne pas lancer `npm audit fix --force` : npm propose notamment des changements majeurs/rétrogradations pour certaines chaînes. Refaire compilation, tests et scan après chaque lot. Aucun paquet n'a été modifié pendant l'audit.

### AUD-07 — Diffusion à 50 conducteurs : nombreuses requêtes séquentielles sous verrou

**Domaine :** performance et délai de livraison des offres. **Confiance :** forte sur la structure, impact temporel non mesuré.

**Preuves :** [dispatch.service.ts](../../src/trip-requests/dispatch/dispatch.service.ts), lignes 227–241 et 269–320 ; [nearby-driver-policy.ts](../../src/trip-requests/dispatch/nearby-driver-policy.ts), ligne 3 ; [notifications.service.ts](../../src/notifications/notifications.service.ts), lignes 590–673.

Une transaction verrouille la demande puis jusqu'à 50 présences. Pour chaque conducteur, plusieurs lectures et écritures sont faites séquentiellement : compte, occupation, KYC/véhicule, capacité du client, offre et notification. L'expiration est calculée pendant la boucle, alors que les offres ne sont visibles qu'après le commit. Le délai de réponse par défaut est de 30 secondes. La voie urgente de notification dispose de cinq workers par processus.

**Impact :** sous charge ou avec une base lente, verrous prolongés, retard de distribution et réduction du temps réellement disponible pour accepter. Le plafond de 50 est une protection utile, mais ne garantit pas le respect du délai. Aucun dépassement de latence n'est affirmé sans mesure.

**Correction :** regrouper les lectures/écritures tout en conservant les vérifications d'autorisation et les verrous nécessaires ; ajuster les lots au budget temporel ; mesurer le délai commit→push et le temps restant à réception. Conserver l'outbox transactionnelle existante. Tester plusieurs demandes simultanées, 50 destinataires par lot et un fournisseur push ralenti avant d'augmenter simplement les workers.

### AUD-08 — Expiration des demandes : chargement et concurrence non bornés

**Domaine :** performance et disponibilité. **Confiance :** forte sur le code, volume réel inconnu.

**Preuves :** [trip-requests.service.ts](../../src/trip-requests/trip-requests.service.ts), lignes 2638–2701 et 2862–2888.

Le cron charge tous les candidats avec `passenger` et `driverOffers`, sans pagination, puis lance un `Promise.all` sur toutes les mises à jour et un autre sur les notifications. `waitForCompletion` évite le chevauchement dans une instance, mais pas ce volume de travail ni les lectures concurrentes de plusieurs instances.

**Impact :** un retard accumulé peut consommer beaucoup de mémoire et remplir la file d'attente du pool PostgreSQL, au détriment des requêtes utilisateur. Les mises à jour conditionnelles limitent les écrasements concurrents, pas la pression sur les ressources.

**Correction :** lots bornés, sélection des seuls champs nécessaires, concurrence limitée et reprise progressive ; coordonner les workers multi-instance. Vérifier sur un jeu volumineux que le trafic HTTP reste servi pendant le rattrapage.

### AUD-09 — OTP : relance ambiguë de l'envoi et protections par numéro incomplètes

**Domaine :** robustesse, expérience utilisateur et maîtrise des coûts. **Confiance :** forte côté backend ; idempotence et quotas du fournisseur non vérifiés.

**Preuves :** [keccel-otp.service.ts](../../src/keccel-otp/keccel-otp.service.ts), lignes 128–145 ; [keccel-otp.module.ts](../../src/keccel-otp/keccel-otp.module.ts), ligne 10 ; [otp.service.ts](../../src/otp/otp.service.ts), lignes 37–78 et 134–155 ; [auth.controller.ts](../../src/auth/auth.controller.ts), lignes 210–222 ; [throttler.guard.ts](../../src/common/guards/throttler.guard.ts), lignes 8–29.

L'envoi POST est retenté une fois après toute erreur, sans distinguer refus définitif et timeout après traitement. Avec le timeout HTTP de 30 secondes, les deux tentatives et la pause peuvent approcher 61 secondes. Le verrou par téléphone protège les opérations simultanées, puis est libéré : il ne constitue pas un quota quotidien. Le contrôle par compte existe pour certains logins, pas comme budget général d'envoi OTP par numéro.

**Impact :** SMS potentiellement répétés et parcours bloquant si le premier envoi a réussi mais sa réponse a été perdue ; spam/cost amplification possible via plusieurs IP. Le comportement exact de Keccel sur un doublon reste à vérifier.

**Correction :** délai de renvoi et budgets par numéro normalisé, plafond global, alertes de consommation ; politique explicite pour les réponses ambiguës. Réessayer une génération uniquement si l'idempotence fournisseur ou une vérification de statut le permet. Ne pas supprimer l'invalidation des anciens challenges sans préserver la séparation des usages OTP.

### AUD-10 — Une interruption peut faire perdre certaines notifications métier

**Domaine :** fiabilité. **Confiance :** forte sur la fenêtre non atomique.

**Preuves :** [trip-requests.service.ts](../../src/trip-requests/trip-requests.service.ts), lignes 2680–2701 et 2808–2845.

Pour le retard de prise en charge, le timestamp `driverPickupOverdueNotifiedAt` est enregistré avant la création de la notification. Pour l'expiration, le changement de statut précède aussi l'appel de notification. Un arrêt ou une erreur entre ces opérations laisse l'état métier modifié sans notification persistée. Les mécanismes de reprise de notifications déjà enregistrées ne couvrent pas cette fenêtre.

**Impact :** le passager peut ne jamais recevoir le push attendu. Le timestamp de retard reste exploitable par l'application, ce qui atténue le problème sans garantir la notification.

**Correction :** enregistrer l'événement outbox avec une clé d'idempotence dans la même transaction que le changement métier. Livrer le push après commit. Tester un crash entre les étapes et vérifier la reprise sans doublon.

### AUD-11 — Les journaux peuvent enregistrer les jetons des liens de suivi

**Domaine :** confidentialité. **Confiance :** forte sur la journalisation, collecte effective dépendante du niveau de logs et des requêtes.

**Preuves :** [tracking.controller.ts](../../src/tracking/tracking.controller.ts), lignes 34–43 ; [logging.interceptor.ts](../../src/common/interceptors/logging.interceptor.ts), lignes 40–92 ; [api-exception.filter.ts](../../src/common/filters/api-exception.filter.ts), lignes 308–309.

Le suivi public est accessible avec un jeton dans le chemin. Le logger et le filtre d'exception utilisent l'URL originale, sans masquer ce segment. Le niveau de logs peut limiter les traces de succès, mais les erreurs conservent ce risque.

**Impact :** une personne ayant accès aux logs peut obtenir un lien donnant accès aux informations de suivi tant qu'il reste valide. Ce n'est pas une exposition publique automatique de CloudWatch.

**Correction :** journaliser le gabarit de route et masquer les segments/paramètres sensibles ; conserver le requestId pour le diagnostic. Tester les chemins de succès, refus, erreur et requête interrompue. Vérifier également la collecte des URL dans les traces d'observabilité.

### AUD-12 — La nouvelle migration peut attendre ou retenir des verrous sans budget local

**Domaine :** robustesse du déploiement et disponibilité. **Confiance :** forte sur le SQL ; durée dépendante du volume et des transactions concurrentes.

**Preuves :** [1780000074000-BroadcastDriverRequests.ts](../../src/database/migrations/1780000074000-BroadcastDriverRequests.ts), lignes 4–16 ; [typeorm-options.ts](../../src/database/typeorm-options.ts), lignes 113–120 ; [deploy.yml](../../.github/workflows/deploy.yml), étape migrations à partir de la ligne 141.

La migration retire un index, crée des index ordinaires et ajoute une colonne, sans fixer ses propres `lock_timeout`/`statement_timeout`. Les connexions de migration ne reçoivent volontairement pas les budgets API. Un `CREATE INDEX` ordinaire peut bloquer les écritures sur la table pendant sa construction ; les DDL peuvent aussi attendre des transactions existantes.

**Impact :** sur des tables importantes ou occupées, déploiement prolongé et erreurs HTTP dues aux attentes SQL, même avant le remplacement des tâches API.

**Correction :** tester sur un volume représentatif, ajouter des budgets adaptés et préparer une stratégie de reprise. Si les index doivent être créés concurremment, traiter explicitement les contraintes de transaction et les index invalides en cas d'échec ; ne pas ajouter seulement le mot-clé à une migration transactionnelle. Aucun changement du workflow de production n'est nécessaire pour commencer par qualifier et améliorer cette migration localement.

## Protections à conserver

- JWT liés aux empreintes enregistrées et contrôles de statut de compte ; le défaut AUD-01 concerne l'atomicité de rotation, pas l'absence de contrôle.
- Verrous et idempotence sur les retraits, protection contre la double dépense et rapprochement des versements ambigus.
- Notifications transactionnelles déjà présentes dans plusieurs flux, files de reprise et voie urgente dédiées.
- Pools et délais PostgreSQL bornés pour l'API ; vérification TLS, pas de synchronisation automatique du schéma en production.
- SQL du dispatch paramétré pour les valeurs utilisateur : l'utilisation de SQL explicite n'est pas en soi une injection SQL.
- Séparation liveness/readiness, arrêt ordonné et exécution Docker sous l'utilisateur `node`.
- Quotas persistants KYC AWS, délais d'appel bornés, revue manuelle lorsque les contrôles restent incertains.
- Dans la version locale, `DiditKycService.createSession` ne dépend plus du contrôle de publication de `DiditWorkflowGuard` avant l'appel de création. Le fichier ouvert dans l'IDE n'est donc pas à lui seul la preuve que l'ancien blocage existe encore en production.

### Didit et application mobile

Le fournisseur actif n'est pas modifié. Pour le parcours mobile demandé, le
backend doit garder `KYC_PROVIDER=didit` et `DIDIT_KYC_LAUNCH_MODE=native`.
Ces noms et valeurs sont des exemples de configuration, pas des clés copiées.
La [documentation officielle du SDK React Native](https://github.com/didit-protocol/sdk-react-native)
confirme l'utilisation de `startVerification(sessionToken)` avec le jeton créé
par le backend ; l'identifiant de session seul n'est pas un jeton SDK.

Le backend rejette une réponse native sans jeton avec
`KYC_SDK_TOKEN_UNAVAILABLE`, avant toute modification du dossier local. Il ne
rejoue pas automatiquement la création payante. Le lien de la même session reste
présent quand fourni, pour compatibilité ; le mode `hosted` reste disponible
explicitement pour les anciens clients ou la cible Web. **La nouvelle application
mobile n'utilise plus ce mode hébergé** : elle indique l'erreur de configuration
si le backend ne lui transmet pas de jeton SDK. Pas de navigateur après une
erreur SDK ; un module absent demande une version native complète.

Test local : utiliser le backend local configuré Didit, recharger le code mobile
dans une build native Android/iOS contenant le SDK (pas Expo Go), puis lancer le
KYC depuis le profil. Vérifier caméra, annulation, reprise, erreur réseau et
synchronisation du statut après retour. Ne pas partager jeton SDK, clé API,
selfie ou document dans les logs. Ces essais physiques restent à faire ; les
14 tests JavaScript mobiles réussis utilisent des modules natifs simulés.
Les anciennes installations des stores conservent leur logique de repli tant
que leur code n'est pas mis à jour ; aucun changement distant n'a été appliqué.

### Paramètres OTP optionnels

Valeurs par défaut : `OTP_SEND_COOLDOWN_SECONDS=30`,
`OTP_SEND_PHONE_HOURLY_LIMIT=5`, `OTP_SEND_PHONE_DAILY_LIMIT=10`,
`OTP_SEND_GLOBAL_DAILY_LIMIT=10000`. Les fenêtres de compteurs commencent à leur
première réservation (une heure / 24 heures), pas à minuit. Le plafond global
est à calibrer selon le budget réel ; il n'est pas une mesure de consommation.
Les clés téléphone sont hachées, tous les usages/endpoints passant par
`OtpService` partagent les compteurs. Une erreur Redis ferme l'envoi (503), un
budget atteint renvoie 429 avec `retryAfterSeconds`. Un refus de quota ne détruit
pas le challenge précédent. Les erreurs fournisseur ambiguës ne remboursent
pas la réservation. Aucun nouveau paramètre n'est obligatoire pour démarrer.
